# Описание целевой архитектуры

**Версия:** 1.1  
**Дата:** 2026-11-26  
**Контекст:** Целевое состояние (TO-BE) для платформы AdScale (SaaS для цифровой рекламы, RTB, аналитика, отчётность) с учётом C4 Container Diagram.  
**Цель:** Обеспечить 50 000 RPS, SLA 99.9%, низкую latency, горизонтальное масштабирование и мультирегиональное развёртывание.

## 1. Бизнес-требования и ограничения

- **Нагрузка:** 50 000 запросов в секунду (RPS) в пиках.
- **SLA:** 99.9% доступности.
- **Latency:** p95 для RTB Hot Path < 80 мс.
- **Масштабирование:** Горизонтальное, автоматическое.
- **Интеграции:** DSP‑площадка (OpenRTB), внешние партнёры, аналитика.

## 2. Архитектурный стиль и принципы

- **Микросервисная архитектура** с чёткими границами по доменам (Advertiser, Ad Server, Financial, Analytics, Statistics).
- **Событийно-ориентированная обработка** (event-driven) через Apache Kafka 3.x.
- **CQRS** для разделения потоков чтения/записи в аналитике и отчётах.
- **Hot Path isolation:** выделенный контур RTB (<80 мс) с Cache (Redis 8.x), Auction Engine (C++), Delivery Service (Node.js).
- **Resiliency:** повторные попытки, circuit breaker, fallback, таймауты.
- **Observability:** метрики, логи, трейсы, алерты по SLO.

## 3. Высокоуровневая структура (C4 Level 1: System Context)

- **AdScale Platform** — ядро платформы.
- **External DSP** — интеграция с DSP‑площадкой (OpenRTB bid-requests/responses).
- **Publishers** — сайты/приложения, показывающие рекламу.
- **Advertisers** — рекламодатели (веб‑интерфейс, API).
- **Analytics & Reporting** — витрины данных, BI‑системы.
- **Identity & Auth** — провайдер аутентификации (OIDC).

## 4. Контейнеры (C4 Level 2: Container Diagram)

### API и шлюз
- **GateAPI (API Gateway)** — маршрутизация, rate limiting, auth, TLS termination.
  - Обрабатывает запросы от Рекламодателя, Пользователя, DSP‑партнёра.

### Домен рекламодателя и кампаний
- **Advertiser Service** — управление кампаниями, бюджетами, ставками.
  - **Advertiser Dashboard (Node.js + JavaScript)** — Web UI для управления кампаниями и отчётностью.
  - **Advertiser DB (PostgreSQL)** — хранение сущностей кампаний, ставок, профилей.
  - **Replica Advertiser DB (PostgreSQL)** — чтение для отчётов и фоновых задач.
  - Взаимодействие: CRUD‑операции через JDBC (чтение/запись), gRPC для внутренних вызовов.

### RTB Hot Path (<80 мс)
- **Ad Server (C++, Go)** — приём HTTP‑запросов, определение пользователя, подбор кандидатов в рекламу.
- **Cache (Redis 8.x)** — хранение кампаний, ставок, бюджетов, профилей для быстрого доступа.
- **Auction Engine (C++)** — взвешивание ставок, применение бизнес‑правил, расчёт победителя аукциона.
- **Delivery Service (Node.js)** — формирование HTML/JS‑разметки баннера и HTTP‑ответа.
  - Все компоненты Hot Path оптимизированы для минимальной задержки; синхронные JDBC‑запросы к БД минимизированы, данные преимущественно из Redis.

### Финансы и биллинг
- **Financial Service** — управление балансами, списание средств, выставление счетов.
  - **Financial Business Logic (Go)** — обработка транзакций, управление бюджетами.
  - **Financial DB (PostgreSQL)** — запись транзакций.
  - **Replica Financial DB (PostgreSQL)** — чтение балансов.
  - Взаимодействие: gRPC для внутренних вызовов, JDBC для доступа к БД.

### Статистика и трекинг
- **Statistics Service** — сбор и обработка событий показов и кликов.
  - **Stats Business Logic (Python)** — обработка событий, агрегация.
  - **Stats DB (PostgreSQL)** — хранение событий показов и кликов.
  - Прямая запись событий, интеграция с Kafka для потоковой обработки.

### Аналитика
- **Analytics Service** — построение отчётов, выполнение тяжёлых аналитических запросов.
  - **Analytics Business Logic (Python)** — формирование отчётов, агрегация.
  - **Analytics DB (PostgreSQL)** — хранение агрегированных данных.
  - **Replica Analytics DB (PostgreSQL)** — чтение для аналитических SQL‑запросов.
  - Взаимодействие: gRPC для внутренних вызовов, JDBC для доступа к БД.

### Очереди и события
- **Apache Kafka Cluster (Kafka 3.x)** — шина событий (кампании, ставки, клики, статусы).
  - Топики: `campaign.events`, `bid.events`, `tracking.impressions`, `tracking.clicks`.
  - Хранение: минимум 7 дней для потоковой аналитики.
  - Все сервисы публикуют события в Kafka; потребители обрабатывают асинхронно.

### Хранилища данных
- **PostgreSQL Clusters** — OLTP для всех доменных БД (Advertiser, Financial, Stats, Analytics).
  - Паттерн Master‑Slave: 1 мастер, реплики на чтение.
  - Реплики используются для отчётов и фоновых задач (снижение нагрузки на мастер).
- **Redis Cluster (Redis 8.x)** — кэширование сессий, конфигураций, счётчиков, rate limiting, данные для RTB Hot Path.
  - Шардирование по ключам, автоматическая балансировка.

### Инфраструктура и надёжность
- **Service Mesh (Istio)** — mTLS, трафик‑менеджмент, observability.
- **CI/CD** — автоматизированные деплои, канареечные релизы, blue‑green.
- **Backup & DR** — регулярные бэкапы БД.

## 5. Потоки данных и сценарии

1. **Создание кампании:** Рекламодатель → GateAPI → Advertiser Service → Advertiser DB (Master) → Kafka (`campaign.events`).
2. **RTB‑аукцион (Hot Path):** Пользователь → GateAPI → Ad Server → Redis (кэш кампаний/ставок) → Auction Engine → Delivery Service → Publisher.
3. **Трекинг кликов:** SDK/пиксель → GateAPI → Statistics Service → Kafka → Stats DB.
4. **Финансы и биллинг:** Financial Service → Financial DB (Master) → Kafka → Replica Financial DB.
5. **Отчётность:** Analytics Service → Replica Analytics DB + Replica Advertiser DB.

## 6. Надёжность и масштабирование

- **Autoscaling:** HPA по CPU/запросам.
- **Rate limiting:** на уровне GateAPI и Redis.
- **Circuit Breaker:** для внешних вызовов и медленных зависимостей.
- **RTB Hot Path:** выделенные ресурсы, минимизация сетевых вызовов, кэширование в Redis, синхронные JDBC‑запросы только при необходимости.

## 7. План миграции и этапы перехода к TO-BE

1. **Этап 1 (AS-IS → Intermediate):** модульный монолит, модули имеют чёткие границы, изолированная схема данных, публичные интерфейсы, архитектурные тесты.
2. **Этап 2 (Intermediate → TO-BE):** декомпозиция на микросервисы, запуск Kafka, разделение чтения/записи, Redis Cluster, выделение RTB Hot Path.

## 8. Риски и меры снижения

| Риск | Мера снижения |
|------|---------------|
| Рост latency в RTB Hot Path | Выделение отдельных ресурсов, кэширование в Redis, минимизация синхронных вызовов |
| Потеря событий в Kafka | Гарантия at‑least‑once, идемпотентность потребителей |
| Перегрузка БД | Реплики для чтения, кэширование, пагинация |
