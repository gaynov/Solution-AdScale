
# ADR-001: Стратегия эволюции архитектуры (от монолита к микросервисам)

**Дата:** 2026-11-18

**Статус:** Предложено

## Контекст

AdScale ожидает значительный прирост пользователей к концу года. Планируется интеграция с крупной DSP-площадкой. Ожидается рост нагрузки до 50 000 RPS. Текущая система — монолит на C++/Go/Python/Node.js с единой PostgreSQL.

Ключевые архитектурные драйверы:
- Нагрузка: 50 000 RPS, P95, задержка <80 мс.
- Консистентность: нулевые потери транзакций для Financial Service (критично для бизнеса).
- Доступность: SLA 99.9%.
- Сроки: 3 месяца (промежуточное решение), 12 месяцев (целевое решение).
- Команда: backend-, frontend- и DevOps-разработчики, тестировщики, дизайнеры, сотрудники службы поддержки и менеджмент — всего 35 человек. Выделенного SRE-инженера, технического писателя и бизнес-аналитика в компании нет.
- DevOps: CI/CD нет.

Рассматривались три альтернативы:
1. Оставить в составе единого монолита.
2. Рефакторинг в модульный монолит с изолированными границами.
3. Выделение в отдельный микросервис.

### Альтернатива 1. Единый монолит
Плюсы: минимальные изменения, быстрый time-to-market.

Минусы: нет изоляции ресурсов, при пике бронирование конкурирует за пул потоков и подключения к БД с другими модулями (аналитика, отчёты и т.д.). Нет чётких границ — риск регрессий при изменении других модулей.

### Альтернатива 2. Модульный монолит
Плюсы: чёткие границы модулей, изолированные схемы данных, публичные интерфейсы (Facades), готовность к будущему выделению в микросервис, сохранение ACID-транзакций.

Минусы: требуется дисциплина тестирования (ArchUnit), накладные расходы на публичные интерфейсы.

### Альтернатива 3. Микросервис
Плюсы: независимое масштабирование, собственная БД.

Минусы: потеря ACID-транзакций (нужен Saga), накладные расходы на сетевое взаимодействие, нет Kubernetes для оркестрации, 3 месяца — слишком мало для построения микросервисной инфраструктуры.

## Решение

В связи с жёстким дедлайном предполагается 2 этапа:

### Промежуточное решение
Реализация системы как модульного монолита в рамках единого приложения. Применяются следующие принципы:
* Модули имеют чёткие границы: **AdvertiserFacade (?!)** как единственная точка входа
  для других модулей.
* Изолированная схема данных: таблицы с данными по кампаниям, финансам, событиям, ставками, аналитике принадлежат только соответствующим модулям. Нет прямых cross-schema JOIN.
* Взаимодействие модулей через публичные интерфейсы (AnalisticFacade, StatisticFacade, FinancialFacade и т.д.).
* Каждый модуль содержит всё необходимое для своей работ (контроллеры, бизнес-логика, репозитории, модель данных). Это domain-driven-структура (bounded context).
* Архитектурные тесты для проверки границ модулей.
* Добавлены health-check- и readiness-точки для подготовки к будущему выделению в микросервис.

Срок: 3 месяца.

### Целевое решение
* Каждый сервис стал отдельным процессом с собственной базой данных и Redis.
* Появление API Gateway для маршрутизации.
* Facade-вызовы (in-memory) уступили место REST/gRPC.
* Для асинхронных событий добавлен Kafka.
* ACID-транзакции заменены на шаблон проектирования Saga.

Срок: 12 месяцев.

## Последствия промежуточного решения

**Положительные:**
* Быстрая доставка: не нужно сразу строить микросервисную инфраструктуру.
* Сохраняются ACID-транзакции. Это важно, например, для Financial Service.
* Чёткие модульные границы снижают риск регрессий.
* Подготовка к эволюции: на следующем этапе модули можно выделить в микросервисы с минимальными изменениями.

**Отрицательные:**
* Невозможно масштабировать модули независимо.
* Единая PostgreSQL остаётся «бутылочным горлышком» при экстремальных пиках (>18 000 RPS).
* Команда должна соблюдать дисциплину модульных границ.

**Риски:**
* Если пиковая нагрузка в каком-либо модуле превысит 18 000 RPS, потребуется досрочное выделение модуля в микросервис. Оценка разработки — 2–3 недели при наличии чётких интерфейсов.
* Конкуренция за пул подключений к PostgreSQL при одновременном пике бронирования и аналитических запросов.

## Последствия целевого решения

**Положительные:**
* Быстрая доставка: не нужно сразу строить микросервисную инфраструктуру.
* Отдельная БД для каждого сервиса, отсутствие конкуренции за пул подключений.
* Подготовка к эволюции: на следующем этапе модули можно выделить в микросервисы с минимальными изменениями.
* Асинхронное взаимодействие повышает отказоустойчивость и снимает жёсткую зависимость между сервисами.

**Отрицательные:**
* Медленная доставка: строительство микросервисной инфраструктуры займёт 1 год.
* Требуются ресурсы на разработку и поддержание микросервисов. В компании должна быть развитая DevOps-культура и необходимые специалисты.
* Потерянные сообщения, для обработки которых понадобится Dead Letter Queue.

**Риски:**
* Данные и консистентность. Замена единственной ACID-транзакции не гарантирует консистентность. Решение: использование паттерна Saga.
* Опасность потери сообщений при асинхронном обмене данными. Решение: правильная классификация сообщений и выбор подходящей модели.
* Диагностика ошибок становится более сложной. Требуется внедрение трассировки, метрик и корреляции логов.
